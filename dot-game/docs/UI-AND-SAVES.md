# Independent UI and persistence notes

The portrait and scene are original SVG / Canvas primitive drawings. No supplied images, prior implementation, structured monster dataset or generated constants are used. All assets are inline/local and there are no third-party runtime requests. Sound is generated by Web Audio only after the user enables it; it defaults off. Reduced-motion preference is honored, with an explicit setting.

## Persistence

The stable game and each `/candidates/<version>/` have distinct localStorage save, settings and tab-lease keys. Browser QA of a candidate must not overwrite the accepted game's progress. Save schema is validated by the independent engine. Import has a 2 MB bound, validation before confirmation and replacement, and only runs in the active owning tab. Import/refresh safely restores to town, per engine design. This is deliberately different from ordinary hidden-tab pause: switching away and back keeps the same in-memory battle if another tab has not changed the stored state.

The visible tab takes a short localStorage lease, releases on hiding, and prevents concurrent visible-tab simulation when another lease is active. A stale lease expires after five seconds. This is a best-effort browser coordination measure, not a transactional database; opening two tabs at the exact same instant can race. With localStorage unavailable, progress remains in memory and the player is warned to export. No offline time is simulated.

Malformed existing saves are not silently overwritten: a temporary new game is opened with a notice and autosave blocked until a valid import. Export remains available. Uploaded/imported names are rendered through textContent, not HTML. Equipment and sale controls are disabled during combat rather than pretending an ignored action succeeded.

## Testing limits

`node --test tests/ui.test.mjs` checks static asset locality, literal DOM bindings, defensive save boundaries and essential controls. It does not replace rendered browser and actual interaction QA. Desktop/mobile browser checks and live deployment results must be recorded separately.
