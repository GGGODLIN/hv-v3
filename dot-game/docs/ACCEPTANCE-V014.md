# v0.14 independent gear-set acceptance

Status: source-level GO after one narrow pending-metadata defect was repaired. This is not a browser acceptance or publication receipt. Parent aggregate checks, exact source backup, candidate UI play and root release evidence are separate.

## Scope and provenance

Three fixed gear-only presets A/B/C reference the existing weapon, armor and accessory IDs. This is a deliberately narrower adaptation than original HV Equipment Sets or Personas: it does not copy attributes, abilities, tactics, battle inventory or quickbars. Original research/source distinctions are recorded in the feature guide and ORIGINAL-HV.md.

Saving explicitly locks the three current items. All preset references prevent unlock/disposal; clearing or replacing a preset retains old locks until the player deliberately unlocks them. This is an explained safety adaptation, not an asserted original locking rule. No item, stat, currency, proficiency, ability allocation, combat coefficient or random roll is generated by a preset.

The independent `tests/gear-sets-acceptance.test.mjs` passes **31/31** tests. It includes an isolated exact copy of our accepted v0.13 engine/loot, with SHA-256 provenance at `tests/fixtures/v0.13/PROVENANCE.md`. This is this project's own prior source, not excluded third-party game code.

## Independently verified contracts

- Three presets store only three existing item IDs each. A→B→A preserves the complete owned-item multiset, including all individual stat/roll/lock records. Multiple presets may share references without adding storage or copies.
- At a full 120-item inventory, replacing all three equipped slots still succeeds by exchanging owned objects. Shared active presets do not require a spare slot.
- Overwriting or clearing changes references only. Formerly referenced items remain locked; clearing one of two shared presets does not remove the remaining protection. Clearing the final preset omits the optional field.
- Preview reads deeply frozen state, returns detached records/stats and cannot be used to inject attack or alter references. The application quote binds exact owned gear, current loadout and relevant build state.
- Missing or mutated target/current gear, altered preset, changed lock or non-camp mode makes stale application a complete no-op. Applying an already active preset or repeating the same application does not heal, write logs, advance RNG or create a fresh action.
- Battle, defeat, intermission and unknown modes refuse save, apply and clear without healing. Invalid payload getters do not execute.
- Every disposal path (`sell`, `sellCommon`, `sellSafe`, `sellSelected`) and lock toggle preserves referenced gear even in a deliberately damaged live fixture whose item lock was cleared. Such a fixture is not a normally accepted save. Unknown metadata fails closed rather than stripping protection.
- Strict imports reject empty/unknown preset maps, unsupported fields, inherited/hidden/accessor data, repeated/wrong-slot IDs, missing references, unlocked references, pending-only references and duplicated ownership. No fabricated replacement item or partial application repairs an invalid import.
- Valid reload retains exact reference maps and the existing item canonicalization. In particular, the pre-existing validator adds `weaponFamily:null` to the unknown starter weapon; equality is checked against the accepted v0.13 validator rather than falsely treating that old normalization as new data loss.
- The old v0.13 reader does **not** understand presets and drops their metadata, but retains the explicit item locks. This is not full backward-compatible preset recovery. Refresh old writer tabs and retain an export.

## Defect found and repaired

The first implementation validated held gear but checked pending loot only for duplicate IDs. Because exact preview serialized the pending list, a synthetic unsupported `description` getter on a pending record executed and the preview remained available. This violated the intended pure/fail-closed preview contract even though normal validated saves do not contain accessors.

The final engine checks every pending record's supported descriptors and the existing eight-item pending cap before constructing a quote. The independent regression confirms unavailable preview, no application and zero getter executions. This is a narrow record-validation correction, not a claim of arbitrary malicious Proxy support.

This is **engine-earned**, not browser-earned or fabricated save progress. Seeds29/42/77 each complete30 normal expeditions using only public create/action/advance APIs and a deterministic highest-score equipment policy. No resources, level or item statistics are injected. The score policy is merely reproducible acquisition, not a new claim that score captures weapon proc or counter utility.

For each earned profile, save A from the currently equipped gear, manually equip one owned alternative per slot, save B, then apply A. A subsequent matched expedition also stays equal at every input and wins on both branches. Reload retains the references and item records under the established canonicalization.

This demonstrates fewer repeated equipment operations, not stronger generated loot, extra inventory, better RNG or a guaranteed combat advantage.
